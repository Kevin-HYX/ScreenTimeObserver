# 开源方案对比：屏幕时间采集链路（M1）

日期：2026-09-15｜对照对象：本项目 M1「搭好常驻采集器并跑通首日数据」

结论先行：**我们的方向与业界主流一致，M1 不必推翻；但有 3 处小改值得现在就吸收**（空闲阈值、事件驱动采集、守护与暂停），另有 4 个产品点留到 M2/终点阶段。

## 二、逐维度对照

### 1. 采集机制：轮询是主流默认，事件驱动是更优解

- ActivityWatch 的窗口 watcher 默认 **poll_time = 1.0 秒**；AFK watcher 默认 **5 秒轮询 + 180 秒判空闲**。
- 纯轮询的固有缺陷被反复讨论：定时器精度决定了下限，**两次采样之间的瞬时切换会整段丢失**。
- 正解是把 SetWinEventHook(EVENT_SYSTEM_FOREGROUND) 当主通道（每次前台窗口变化都触发回调，零轮询成本），**并同时挂 EVENT_SYSTEM_MINIMIZEEND**，因为从最小化恢复时不会再发 FOREGROUND 事件；钩子为 OUTOFCONTEXT 时必须有消息循环，且回调对象要保活、不能被回收。

对 M1 的意义：**5 秒轮询不该是精度上限，只该是兜底对账**。事件驱动 + 低频对账，同时解决「空洞」与「开销」两个验收项。

### 2. 数据模型：bucket + heartbeat 合并 vs 我们的行式 JSONL

- ActivityWatch 把数据放进 bucket，每个事件是 {timestamp, duration, data}；watcher 以 **heartbeat** 方式上报，服务端在 pulsetime 窗口内把 data 相同的连续 heartbeat **合并成一条长事件**（官方明说这是为了省存储与磁盘 IO）。查询期还有 flood 操作把事件之间的空白补掉，用来消解「空洞」。
- 事件类型有约定：currentwindow {app, title}、afkstatus {status}、web.tab.current {url, title, audible, incognito}。
- Tockler 走另一条路：直接存 begin/end 的 TrackItem，并**把跨午夜的活动拆成两天**，保证按天统计准确。

对我们的取舍：我们的「状态指纹变化才写 + 60 秒心跳」与 heartbeat 合并是同一思路，但**行式 JSONL 更符合「复盘时直接读得懂」**（不用先起服务、不用学查询语言）。保持不变；M2 再考虑合并/API 层。
**要吸收的是跨天处理**：日文件按天切分时，第二天首行只是一条「变化点」，直接读会出现一段假空洞。建议每天首行写一条承接记录（carry-over），把上一天最后状态的延续显式表达出来。

### 3. 空闲判定：我们的阈值比业界严

- ActivityWatch：**180 秒**无输入才算 AFK（可配），5 秒轮询一次。
- Tockler：把系统状态显式建成三态 **ONLINE / IDLE / OFFLINE**，并对睡眠唤醒单独处理：睡眠时保存状态，唤醒后把睡眠时长记为 OFFLINE 段，再恢复跟踪。

对我们的取舍：我们原定 60 秒判 idle 偏严，**「看着屏幕思考两分钟」会被记成空闲**。建议判定阈值对齐 180 秒；同时**保留逐行记录 idle_sec**，这样阈值日后可以离线重算——这一点我们比 ActivityWatch 更细（它只记 status，不记秒数），是我们的优势，不要为了对齐而丢掉。
另外 Tockler 的 OFFLINE 段值得抄：关机/睡眠期间不写空洞，但数据里要能标注出「这段没记录是因为机器睡了」。

### 4. 自启与守护：光有自启不够

- ActivityWatch 的做法是 **aw-qt 托盘程序当 supervisor**：统一拉起 server 与 watcher、崩溃了能重启、菜单里能单独勾选/取消某个 watcher；配置里用 autostart_modules 决定开机拉起谁。
- 社区结论很直白：**如果绕过 aw-qt 直接用 systemd 之类的服务拉起，一旦 watcher 崩了既不会通知你也不会自动重启**。
- 官方还提供「暂停记录」能力：不想被记录的时段，直接在托盘里取消勾选对应模块即可，作为一种低技术含量的隐私兜底。

对我们的取舍：M1 的验收是「重启后自动恢复、无需人工干预」。**只配计划任务开机自启，等于把「进程意外退出」变成了必须人工发现的故障**。建议加最小守护件：计划任务保活的启动器 + 一个暂停开关（例如存在 pause 文件则跳过写入）。成本很小，但直接决定「建好不用」这个风险项。

### 5. 隐私控制：脱敏要发生在落盘之前

- aw-watcher-window 有 exclude_title（干脆不记标题）。
- awatcher 的 filters 更强：按 match-app-id / match-title（正则）命中后，把应用名或标题**替换成占位值**再上报，例如命中敏感词的标题统一替换为 Unknown。
- ActivityWatch 官方给 AI/agent 用的文档里也写了原则：**数据留在本地，先压缩成小摘要再交给模型**，不要用「分析我的一生」这类宽泛提示把全量数据丢给模型。

对我们的取舍：我们的边界是「不截图、不存网页正文」，标题本身仍可能带敏感信息（聊天窗口、邮箱、文档名）。**脱敏规则必须放在写入之前**，否则 M2 只能面对已成脏数据。M1 只需预留配置位（标题正则 → 占位符），不必现在写复杂规则。

### 6. 数据访问：文件 → API → 查询语言 → MCP

- ActivityWatch 服务端提供 REST API：bucket 增删查、events 读写、heartbeat 上报、**查询语言**（过滤/合并/分组/变换）。Web UI 里还有 query explorer 可以即时调试查询，并支持导出 JSON。
- 已经有第三方 **MCP server** 把 bucket 列表、事件读取、查询执行封装成工具，供 AI 直接调用。

对我们的取舍：M1 的「AI 可直接读取」用 JSONL 就够（甚至更好读）。**这条留到 M2**：如果清洗后要做多轮分析，把「读文件」升级为「本地 API / MCP 工具」会更省 token 也更少出错。

### 7. 标题不够细：两条既有正路

- **浏览器扩展**（aw-watcher-web）能直接拿到活动标签的 title、URL、是否发声、是否无痕，权限只需访问本机 127.0.0.1 的服务端口。这比 UIA 挖控件层级可靠得多。
- **媒体会话 watcher** 用系统报告的会话信息（正对应我们那条「媒体会话旁路」任务）补视频/音乐标题，覆盖飞书、腾讯视频这类标题不细的应用。

对我们的取舍：M1 明确不要求解决（用户已确认此项无所谓），但**架构上别把路堵死**：数据里保留 window_class 与进程名，M2 加扩展/媒体 watcher 时才有对齐键。

## 三、可借鉴的产品点，分三档

### A. 现在就吸收（低成本，直接提升 M1 成败）

1. **事件驱动优先 + 低频轮询对账**：SetWinEventHook(FOREGROUND + MINIMIZEEND) 作主通道，5 秒轮询兜底。同时间接回答关键路径 1 的「开销可接受」。
2. **空闲阈值从 60 秒改到 180 秒**，但逐行 idle_sec 照记（判定阈值可事后重算）。
3. **加最小守护 + 暂停开关**：计划任务保活启动器 + pause 开关，避免「进程静默死掉没人知道」。
4. **跨天承接记录**：每天首行显式表达「延续上一天最后状态」，消灭跨天假空洞。
5. **显式区分「没采集」与「采集到空闲」**：保留 locked 字段，并把睡眠/关机段标记为 offline，而不是留空。

### B. 进 M2 备选（现在只预留配置位与字段，不实现）

6. **标题脱敏规则**（正则 → 占位符），落盘前生效。
7. **浏览器扩展 + 媒体会话 watcher** 补标签级/媒体级细节。
8. **数据访问升级为本地 API（或 MCP 工具）**，配一个查询层。
9. **可视化回看**（时间轴/仪表盘）——到「终点｜复盘默认从这份记录出发」阶段再要。

### C. 明确不学

10. 键鼠内容记录（selfspy 路线）——超边界。
11. 云端同步、多端、手机——边界外。
12. 行为分类与生产力评分（RescueTime 式打分）——边界外。

## 四、对当前 M1 方案的净结论

**保持**：JSONL 行式落盘（变化 + 心跳）、纯本地、不截图、不记内容、单实例互斥。

**改动 3 处**：① 空闲阈值 60 秒 → 180 秒；② 采集改为事件驱动 + 5 秒对账轮询；③ 增加守护与暂停开关。

**新增 1 项**：跨天承接记录 + offline / locked 段的显式标注。
